# 在线咨询长期聊天、AI 转人工与知识沉淀设计

日期：2026-10-22

项目：AI 智能医疗问诊平台（Vue 3 + FastAPI）

阶段：设计文档，供评审；尚未实施

## 1. 目标与已确认需求

将在线咨询从一次性留言回复改为患者与医生之间可持续沟通的聊天，并把医生筛选出的咨询内容整理为可复用的知识，供后续 AI 问诊检索参考。

以下行为已由用户明确确认，实施时不得改变：

1. 同一患者与同一医生始终共用一段长期聊天；双方可持续发送消息，历史长期保存，不因医生回复而结束。
2. 发起咨询前必须选择医生。下拉选项在姓名后显示科室、职称，例如“张医生 · 心内科 · 主任医师”。
3. AI 问诊对话最底部增加“转人工咨询”。跳转在线咨询、选定医生后，系统自动整理并发送本次 AI 问诊摘要，无需患者预览、编辑或二次确认。
4. 医生可勾选聊天中的一条或多条完整消息。每个聊天气泡是一条消息；不要求勾选全部聊天，不以固定一问一答为选择单位。
5. 点击“存入知识库”后，由大模型整理选中的内容。医生看到并修改的是正常排版的知识文章，不是 Markdown 源码。
6. 医生确认文章后，系统在后台生成 Markdown 文件、保存到知识库并向量化。

其余技术与边界规则是本设计的实施建议，与上述已确认需求分开表述。本文不包含实施任务排期或已经完成功能的声明。

## 2. 范围与方案选择

本次包含患者端聊天、医生端聊天与文章确认、AI 转人工、知识入库、历史迁移，以及受到影响的管理员页面、统计和权限检查。

第一版采用文本消息，支持历史分页、未读提示和自动获取新消息。图片、文件、语音、撤回、群聊、医生之间转接、短信或站外通知不在本次范围内。

### 2.1 会话模型

| 方案 | 特点 | 结论 |
| --- | --- | --- |
| 继续在原工单上增加追问字段 | 改动看似较少，但消息角色、历史合并和未读处理持续依赖旧工单语义 | 不采用 |
| 新增长期会话与统一消息模型，迁移旧内容 | 用患者与医生唯一关系承载聊天，消息按统一结构保存，历史可追溯 | 采用 |
| 与 AI 问诊共用同一会话和消息表 | 减少表数量，但人工参与者权限与 AI 角色、生成状态容易混杂 | 不采用 |

### 2.2 消息更新

第一版使用增量轮询：活动聊天每 3 秒获取新消息，会话列表每 10 秒更新；页面隐藏时暂停，恢复可见后立即同步。失败后退避，最长 30 秒；发送成功后立即同步。

这能满足当前项目的聊天需求，沿用 HTTP 鉴权。消息可能有数秒延迟，不承诺即时推送。以后可替换为 SSE 或 WebSocket，数据库与发送接口保持稳定。

## 3. 患者与医生聊天

### 3.1 发起与延续

普通入口流程：在线咨询 → 选择医生 → 输入内容并发送 → 创建或进入双方唯一聊天。

- 选中医生时先查找已有会话；没有会话时显示聊天准备页，不因打开下拉框或取消操作产生空会话。
- 首次发送消息时，在事务中创建会话并写入消息。数据库对 `(patient_id, doctor_id)` 建唯一约束，防止多个窗口或并发请求创建重复会话。
- 医生下拉框支持姓名搜索和分页加载，不沿用固定读取前 100 名医生的限制。
- 只允许选择启用的医生；提交时重新验证医生状态。缺失科室、职称时显示“科室未设置”“职称未设置”，不展示空分隔符。
- 已有医生停用时，历史仍可查看，聊天提示“该医生暂不可接收消息”；不允许新发消息、转入摘要或开展知识提取。恢复启用后可继续。
- 不增加“回复即完成”“关闭会话”等会阻止后续沟通的状态。

### 3.2 页面与消息

桌面端采用会话列表与聊天区并列；手机端先展示会话列表，进入会话后展示聊天页并可返回。沿用项目现有样式和响应式导航。

会话列表展示对方姓名、最后一条消息摘要、最后消息时间、未读数；患者端同时展示医生科室与职称。按最后一条消息的顺序排列。

聊天区展示姓名、身份、时间、正文和消息状态。文本支持换行；中文输入法选字时不得触发发送。发送区和历史加载均适配手机。

- 每次最多加载 50 条消息，通过消息序号游标向前加载历史或向后获取新消息，避免一次返回全部记录。
- 收到新消息时，用户位于底部才自动滚动；正在阅读历史时显示“有新消息”，不强行改变阅读位置。
- 待发送和失败消息保留输入内容并提供重试。服务端确认保存后才显示发送成功。
- 每次发送生成稳定的客户端请求标识；同一次发送重试只产生一条消息。
- 已读游标只在会话可见且消息实际加载后推进，不能因轮询列表而将所有消息标记已读。

### 3.3 未读与待回复

“未读”与“待回复”分别计算：未读表示对方有尚未读到的消息；待回复表示存在比医生最近一次回复更新的患者消息或转入摘要。医生读过但尚未回复时，仍属于待回复。

医生端提供“全部咨询”“待回复”筛选；回复后只从待回复筛选中移出，仍保留在全部咨询中。系统提示不计入待回复。无需逐条回复才能清除待回复，医生新回复表示本轮已回应。

## 4. AI 问诊转人工

### 4.1 用户流程

1. 在当前 AI 会话的消息末尾、输入区上方展示“转人工咨询”。没有已保存的患者消息时不显示入口。
2. 点击后跳转在线咨询页面并打开医生选择区。路由只携带 AI 会话标识，不携带症状、病史或摘要正文。
3. 选择医生后立即提交转人工任务，进入双方聊天，展示“正在整理问诊摘要，完成后将自动发送”。不增加患者确认步骤。
4. 任务完成后，摘要作为一条新消息自动追加到聊天；双方都能看到“AI 问诊摘要”标记。
5. 已有聊天的原消息保持不变；患者可以继续发送普通消息，不必等待摘要完成。摘要按实际发送顺序加入，卡片注明源会话与摘要范围时间。

AI 正在回复时，入口暂不可点击并显示“请等待本次回答完成”。后端需在 AI 回答保存后明确通知前端“已保存”；不能只凭流式正文结束就认为消息已落库。AI 回复失败时可基于已保存内容转人工，但不得把未保存的部分回复当作完整结论。

### 4.2 摘要内容与范围

“本次”定义为当前 AI 会话中，截至选择医生并提交转人工时已经保存的消息快照，不包含其他 AI 会话，也不自动读取健康档案。

摘要使用通俗中文，包含已有信息中的：

- 患者主要诉求、症状、持续时间及变化。
- 患者自己提到的相关病史、过敏史、用药等背景。
- AI 曾提供的建议，单独标注为“AI 已给出的建议”。
- 尚未明确、需要医生进一步了解的问题。

没有的信息不编造，不将 AI 推测改写为患者事实或医生诊断。每份摘要保留“由 AI 根据本次问诊整理，供医生了解背景”的来源说明。聊天卡片呈现排版内容，不显示 Markdown 源码。

### 4.3 去重、重试与变化

转人工任务以“患者 + 医生 + AI 会话 + 快照截止消息 ID”建立唯一约束。双击、刷新、网络重试或同一快照再次转给同一医生，都返回已有任务与结果，不重复发送。

同一个 AI 会话产生了新消息后，患者再次主动转人工，可追加新摘要；新摘要仍覆盖该会话截至当前快照的内容，并注明“更新的 AI 问诊摘要”。转给另一位医生需要重新选择该医生，分别建立任务。

模型失败或超时时展示“摘要整理失败，请重试”，不发送空摘要，不谎报转交完成。已生成摘要但发送失败时重试发送阶段，不重复调用模型。失败不影响普通聊天。

## 5. 医生从聊天沉淀知识

### 5.1 选择消息

医生在自己的聊天中点击“选择内容”，进入多选模式。每条患者消息、医生消息和 AI 摘要均可独立勾选；系统提示不参与提取。

支持非连续选择，工具栏显示“已选择 N 条”以及“存入知识库”“取消选择”。未选择时禁用入库按钮。选择顺序不影响生成顺序，后端按聊天顺序重新排序。

勾选不自动包含未选消息，也不默认选择全部历史。提示“建议同时选择相关问题和医生回复，便于保留完整背景”，但不强制凑成一问一答。只选择患者问题也可生成待补充文章，不能由模型自行编造答案。

### 5.2 生成与确认页面

点击“存入知识库”后显示“正在整理知识内容”，完成后进入“确认知识内容”页面。说明文字为：

> 已根据您选择的对话整理，请检查内容是否准确。

医生看到正常排版的文章标题、段落、小标题和列表。标题可以直接修改，正文使用所见即所得编辑器，提供段落、小标题、加粗、有序与无序列表等有限格式。

不得使用 Markdown 文本域、源码预览、`#` 标题标记或“编辑 Markdown”等技术文案。也不能只将源码显示区换个名称，就视为满足要求。实际交互应接近编辑普通文章。

文章可按内容使用“问题描述”“相关背景”“医生解答”“适用条件与注意事项”等小标题；没有依据的章节省略或明确说明未提供，不强行补齐。

主要操作：

| 操作 | 行为 |
| --- | --- |
| 重新整理 | 按同一份选中消息快照重新生成草稿；若医生已修改内容，先提醒会覆盖修改 |
| 确认存入知识库 | 保存医生当前确认版本，后台生成文件并向量化 |
| 返回聊天 | 保存当前草稿后返回，可从该会话的“知识整理记录”继续编辑 |

正文变化后自动保存草稿，离开时等待保存完成；保存失败时保留编辑内容并提示重试。草稿带版本号，避免两个窗口互相覆盖。生成结果结构不合法时报告整理失败，不直接展示模型原始输出作为文章。

### 5.3 知识内容规则

- 模型只依据选中的消息快照整理，不额外检索资料，不主动补全诊断、药物剂量或禁忌。
- 去除姓名、电话、证件号、详细地址、账号等身份信息；保留理解建议所需的年龄段、病程等医学背景。文件名也不得含患者身份信息。
- 输入模型前先移除可识别身份字段与明确标识符，生成后再检查；医生确认时提示检查个人信息和内容准确性。
- 明确区分患者描述、医生意见、AI 摘要中的 AI 建议。AI 建议不得自动归入“医生解答”。
- 只有 AI 建议或患者提问时，明确提示“所选内容中没有医生解答，请补充或核实后入库”，医生可以补充并确认；模型不能代替医生编造意见。
- 对个案条件、建议适用范围与不确定性如实保留，不把针对个体的建议改成通用处方。

### 5.4 入库与反馈

医生确认后，将文章结构转换成 UTF-8 Markdown 文件，并建立现有知识文件记录，再解析、分块、向量化。确认后的文章版本锁定，不允许后台重试改变其内容。

医生侧展示业务状态：

| 状态 | 显示文字 |
| --- | --- |
| 已确认、保存文件或排队处理中 | 正在存入知识库 |
| 全部向量写入且可检索 | 已存入，可供 AI 问诊参考 |
| 文件或向量处理失败 | 处理失败，请重试 |

文件已保存但向量化失败时，保留已确认文章与文件，只重试失败阶段。重复确认、网络重试不能创建多个文件。相同会话、相同选中消息集合默认复用已有草稿或入库结果，不重复创建；选择不同消息集合可以形成新文章。

第一版存入平台现有公共知识库，不另建医生私有知识库。医生只能查看和处理自己创建的草稿与入库任务；管理员沿用知识库管理入口维护最终文件，新增来源类型、整理医生和处理状态展示。管理员删除知识文件后，其向量停止检索，来源记录保留“已移除”，不能借旧任务自动恢复已删除文件。

## 6. 后端结构与数据设计

以下为建议模型名称和接口契约，实施中可按项目命名规范调整，但不得改变唯一性、归属和状态语义。

### 6.1 新增数据对象

| 对象 | 主要字段与约束 |
| --- | --- |
| 人工聊天会话 `HumanConversation` | ID、患者 ID、医生 ID、姓名快照、创建时间、最后消息时间、最后消息序号、患者/医生已读序号、最近患者/医生消息序号；患者与医生联合唯一 |
| 聊天消息 `HumanMessage` | ID、会话 ID、会话内递增序号、发送角色与 ID、类型 `text/ai_summary/system`、正文、受限结构化内容、创建时间、客户端请求标识、源任务 ID、旧记录映射；会话内序号唯一 |
| AI 转人工任务 `AiHandoff` | ID、患者与医生 ID、AI 会话 ID、截止消息 ID、消息快照、任务状态、摘要结果、目标会话与消息 ID、错误信息、重试次数；转人工业务键唯一 |
| 知识草稿 `ConsultKnowledgeDraft` | ID、会话 ID、医生 ID、选中消息 ID 列表及快照、集合摘要、文章结构、草稿版本、生成版本、状态、确认时间、知识文件 ID；会话与选择集合摘要唯一 |
| 后台任务 `ProcessingJob` | ID、任务类型、业务对象 ID、状态、当前阶段、尝试次数、租约与执行令牌、下次执行时间、内部错误码；同一业务对象同一阶段仅一个有效任务 |
| 历史迁移映射 `ConsultMigrationMap` | 旧工单/回复 ID、新会话/消息 ID、迁移状态、异常说明；旧记录映射唯一 |

会话内序号通过锁定会话行后分配，分配与消息插入同事务提交，避免并发提交顺序导致增量轮询漏消息。历史展示以会话序号为稳定顺序，同时保留原始时间。

发送角色与身份由登录态确定，不接受前端自报医生身份。AI 摘要属于患者发起的转交消息，显示系统生成标记并计入医生待回复。

`KnowledgeFile` 保留现有类型、路径、分块数、向量状态、上传身份字段，补充来源类型和来源草稿 ID。草稿 ID 与知识文件一一对应；来源会话和消息追溯只对原医生及管理员开放，不放进面向普通用户的向量正文或引用信息。

### 6.2 服务边界

- **聊天服务**：参与者检查、唯一会话、消息保存、游标、未读与待回复。
- **AI 转人工服务**：验证 AI 会话归属、冻结源消息、生成摘要、幂等追加消息。
- **咨询知识服务**：校验选中消息、生成与编辑文章、确认版本、关联来源。
- **知识入库服务**：文章转 Markdown、保存文件与记录、调用现有解析和向量化能力、发布状态及失败恢复。
- **持久化任务执行器**：调度上述耗时操作，维护执行状态和重试，不直接承载聊天权限逻辑。

复用现有模型配置和向量组件。摘要与文章整理使用独立提示词和结构化输出校验，不直接复用 AI 问诊的检索回答提示词，也不把历史聊天当作模型指令执行。

### 6.3 文章表示与后台执行

文章在编辑阶段存为受限结构化 JSON，例如标题、段落、列表等块。前端按结构显示和编辑，后端统一验证并转换为 Markdown。禁止任意 HTML、脚本、嵌入对象和外部图片；第一版正文不支持附件。

沿用 FastAPI/MySQL 部署，增加数据库持久化任务与轻量执行循环，不要求引入 Redis 或 Celery。任务事务提交后再执行；执行器通过租约领取任务，超时任务可恢复。服务启动扫描未完成任务。多个执行器必须使用条件更新和执行令牌，避免旧执行器在租约失效后覆盖新结果。

状态至少区分排队、处理中、成功、失败。生成、保存、向量化、发送分阶段记录；模型暂时失败最多自动重试 3 次（逐次退避），之后显示失败并允许手动重试。校验失败与权限变化不自动重试。

不持有长事务等待模型或向量服务。外部调用采用超时，任务失败不阻塞聊天。

### 6.4 文件与向量一致性

使用服务端生成的安全文件名和固定存储目录；先写临时文件，再原子改名。数据库保存确认版本与目标文件标识，重试复用同一文件 ID，不产生重复文件记录。

向量使用稳定 ID；同一文件的入库与重新向量化串行执行。发生部分写入时清理该文件残留再重建；清理失败必须报错，不能沿用当前吞掉删除异常的行为后仍显示成功。

检索候选必须关联数据库验证知识文件仍存在、已确认且 `vector_status=2`，过滤处理中、失败或已删除文件。现有管理员上传文件视为已审核来源；其成功状态规则不变。候选被过滤后适度扩大召回，直至凑足目标数量或达到检索上限，不能把失败任务的半成品提供给 AI。

数据库、文件系统和 Chroma 不具备跨系统事务，通过稳定业务 ID、分阶段记录和补偿重试保证最终一致。只有全部分块写入成功且发布状态提交后，才显示“已存入，可供 AI 问诊参考”。

## 7. 接口契约

以下路径均在现有 `/api/v1` 前缀下，沿用项目统一响应结构。业务失败使用明确的 HTTP 状态与错误码，不以成功响应掩盖失败。

| 接口 | 职责 |
| --- | --- |
| `GET /consult/conversations` | 按当前患者/医生列出自己的会话，支持分页、待回复筛选 |
| `GET /consult/conversations/by-doctor/{doctor_id}` | 患者查询与指定医生的已有会话；不存在不创建 |
| `POST /consult/conversations/messages` | 患者首次发送，携带医生 ID、正文和请求标识，原子创建或复用会话 |
| `GET /consult/conversations/{id}/messages` | 参与者按 `before_seq` 或 `after_seq` 获取消息，二者不可同时使用 |
| `POST /consult/conversations/{id}/messages` | 参与者发送普通消息，包含请求标识 |
| `PUT /consult/conversations/{id}/read` | 更新本人已读游标，只允许单调递增且不超出有效消息范围 |
| `POST /consult/ai-handoffs` | 患者传入医生 ID、AI 会话 ID；后端校验并固定快照，返回任务状态 |
| `GET /consult/ai-handoffs/{id}` / `POST .../{id}/retry` | 查询或重试本人的转人工任务 |
| `POST /consult/conversations/{id}/knowledge-drafts` | 本会话医生提交消息 ID 集合，创建或复用草稿生成任务 |
| `GET /consult/conversations/{id}/knowledge-drafts` | 医生查看本会话的知识整理记录 |
| `GET /consult/knowledge-drafts/{id}` / `PUT .../{id}` | 查询草稿或使用版本号保存文章；冲突返回 409 |
| `POST /consult/knowledge-drafts/{id}/regenerate` | 使用原快照重新整理，更新生成版本并防止旧结果覆盖 |
| `POST /consult/knowledge-drafts/{id}/confirm` | 幂等确认当前版本，锁定文章并启动文件入库 |
| `POST /consult/knowledge-drafts/{id}/retry` | 重试失败阶段，已经成功或已移除的结果不得重复入库 |

请求仅提供标识，后端重新读取并验证消息来源。不得接受前端拼接的任意聊天文本作为可信来源。旧工单创建和回复接口在切换后停止写入，不允许新旧系统同时产生相互独立的记录。

## 8. 权限、保存与关联功能

- 患者只能访问自己的聊天和转人工任务；医生只能访问自己参与的聊天及自己创建的知识草稿。
- 知识提取中的全部消息必须来自当前会话，不能跨会话混选或冒用消息 ID。
- 转人工必须验证 AI 会话属于当前患者。现有 AI 历史消息读取接口缺少会话归属过滤，应在本次涉及的入口中一并补齐。
- 管理员保留会话管理和知识文件管理权限，不能以管理身份代发患者或医生消息。
- 长期保存的默认行为是不自动清理、不因回复或退出而删除；普通患者和医生不提供消息删除入口。
- 为避免现有级联删除破坏长期聊天，有人工聊天关联的用户或医生禁止硬删除，提示改为停用；管理员咨询页面移除整段聊天的直接删除操作。既有无聊天关联账号的删除规则不由本需求扩展。
- 停用账号不得继续发送、读取受保护接口或生成知识；正常参与方仍能查看已有历史和身份快照。
- 技术日志只记录业务 ID、阶段、耗时与错误码，不输出完整聊天、摘要、草稿或身份字段。

关联页面需要同步调整：

- 医生工作台的待回复统计采用新会话待回复定义；“已回复”统计为存在医生回复且当前无待回复消息的会话数，不再表示咨询结束。
- 患者咨询数量按长期会话数统计；界面说明为“咨询会话”，不再按旧工单数统计。
- 健康档案的可选患者来源改为新会话关系，同时保留预约与既有档案来源。
- 管理员咨询列表改为按会话查看聊天历史，展示双方、最后联系时间和待回复状态。

## 9. 历史迁移与切换

新增表承载新模型，旧 `t_doctor_consult`、`t_doctor_reply` 暂时保留只读。迁移前备份并运行只读检查，生成数量、归属异常、时间异常和缺失账号报告。

迁移规则：

1. 同一患者与同一明确归属医生的多个旧工单合并到唯一新会话。
2. 每个旧工单的主诉转为患者消息；每条回复转为对应医生消息。保留原内容、原时间和旧记录标识，不丢弃标题中的原有文字。
3. 按原时间、旧工单 ID、主诉在回复前、旧回复 ID 的稳定顺序赋予新会话序号。
4. 医生 ID 为空且没有回复的旧记录保留在“历史咨询”只读入口；不创建无医生的新聊天。患者可选择医生并点击“继续咨询”，将原主诉复制一次到新聊天，保留来源映射。
5. 归属为空但回复医生唯一时按该医生归属；归属医生与实际回复医生不一致、涉及多位医生或账号缺失时标记异常，保留只读历史，不擅自将内容展示给另一位医生。
6. 旧系统没有可靠已读信息，不虚构历史未读。初始化已读游标到迁移末尾；待回复按实际最后患者/医生消息计算，因此未回复咨询仍能进入待回复筛选。
7. 迁移脚本通过旧记录唯一映射重复执行不产生重复消息；核对各会话原始消息数量、正文与归属后再切换。

切换期间暂停旧咨询写入，完成最终增量迁移，统一切换前后端，再开放新聊天写入。记录切换时点，禁止双写。

开放新写入之前可恢复备份并回到旧版；开放后禁止直接回退到只能读取旧表的应用，否则新消息不可见。此时优先修复，必要时暂时只读，新表与已产生的数据必须保留。

## 11. 验收标准

### 11.1 长期聊天

- 同一患者和医生首次咨询建立一段聊天；再次选择、刷新、重新登录及并发首次发送均复用同一会话。
- 双方能够多轮交流；医生回复后历史仍可见，患者继续发消息后重新进入医生待回复列表。
- 医生姓名后正确展示科室、职称，超过 100 名医生仍能搜索和选择。
- 消息重试不重复；并发发送不漏消息；长历史分页稳定；查看旧消息不被强制滚动到底部。
- 未读与待回复分别验证，读取消息不能自动替代医生回复。
- 越权读取、发送、跨会话消息操作被拒绝；医生停用后历史可见但不能新增沟通。

### 11.2 AI 转人工

- 入口位于当前对话最底部；点击跳转并先选择医生。
- 选定医生后自动生成和发送，无摘要预览、编辑或二次发送确认。
- 新聊天及已有聊天均正确追加摘要，旧历史不被覆盖。
- 摘要只包含当前 AI 会话快照，区分患者事实与 AI 建议，不混入其他会话或未保存的回复。
- 同一快照重复操作不重复发送；新内容产生后再次转人工可追加更新摘要。
- 模型失败、发送失败、页面刷新与服务重启能查询状态并恢复，失败不阻断普通聊天。

### 11.3 知识整理与入库

- 可选一条或多条非连续消息，系统只整理选中消息并保持原顺序。
- 医生看到的是可直接编辑的文章，页面无 Markdown 源码；编辑后的内容与最终文件内容一致。
- AI 建议不被标成医生意见；只有问题时不编造答案；身份信息不进入知识正文和文件名。
- 草稿保存可恢复，版本冲突不覆盖他人修改；重新整理不会用过期任务覆盖新内容。
- 医生确认前不进入可检索知识库，确认后保存一个 Markdown 文件并完成分块和向量化。
- 重复确认和重试不重复创建文件；向量化失败保留文章与文件；部分写入不能被 AI 检索。
- 成功后能通过相关问题检索到知识，来源可由有权限的医生或管理员追溯；普通用户看不到患者和聊天标识。
- 管理员删除知识文件后停止检索，旧任务重试不能将其复活。

### 11.4 迁移与联动

- 旧主诉和回复按规则完整迁移，同一医患合并；重复运行迁移不增加消息。
- 未分配与异常归属记录保留只读访问，不丢失、不泄露给无关医生。
- 医生工作台、患者统计、管理员咨询列表、健康档案患者选择均使用正确的新关系和统计口径。
- 删除账号或旧工单的路径不能意外清除新聊天历史。

验证应包含后端权限、事务与幂等测试，前端交互测试，真实文件与向量链路联调，以及桌面和移动浏览器验收。浏览器测试按项目约定优先使用 ego 浏览器。模型或数据库不可用时，明确记录未完成的联调范围，不用模拟结果代替真实链路验收。
